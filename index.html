Bring-up and fault isolation

PCB and setup all look good, but the unit still will not come up?


I start by separating test-rig faults from DUT-level faults: power rails, clocks, resets, IO, boot state, control interfaces, and measurement assumptions. Obvious failures are often connectors, harnesses, solder joints, rails, or setup errors.


The less obvious cases still usually reduce to a traceable path problem: a bad DAC channel distorting a signal, a stressed test-box rail dropping under load, or a brown-out condition leaving an MCU looking dead.


The job is to make the failure observable, narrow the fault domain, and stop guessing.

Engagement path: Active probing, bench access, or implementation work can sit inside development support or a defined project. Existing logs and captures can also support a bounded diagnostic start.
Typical entry point: first article bring-up, intermittent behaviour, unclear fault domain.
Bring-up path
  • Engagement path
    • Development support when the DUT needs active probing, implementation, or team integration
    • Diagnostic start when logs, captures, photos, or notes already exist
  • Entry
    • First article, dead-looking DUT, or intermittent behaviour
    • Setup appears correct but the fault domain is unclear
  • Separate setup from DUT
    • Connectors, harnesses, rails, clocks, resets
    • IO levels, contention, pull-ups, protocol assumptions
  • Chase the odd cases
    • Rail drop, brown-out, bad channel, solder joint, boot-state issue
    • Reproduce the symptom, instrument it, then narrow the probe path
  • Exit
    • Fault domain isolated
    • Next measurement, firmware check, rework, or fix path is clear

Validation and engineering test tooling

Have an older ATE setup that is still core to your flow, but no obvious owner left to maintain it?


Maybe the latest hardware revision needs one extra test mode, but the framework feels like a black box. Maybe the team needs a BER reporting tool so hardware engineers get quick feedback instead of pasting raw logs into Excel. Maybe chamber data, humidity, dew point, or long-run stability need to be captured live instead of reconstructed afterwards.


I work on the practical middle layer between bench reality and formal validation: custom scripts, GUI tools, DUT-control utilities, instrument automation, report generation, data capture, and ATE framework updates.


The goal is not tool-building for its own sake. It is faster feedback, fewer manual steps, and test flows that survive the next revision.

Engagement path: A repeatable validation flow can be delivered as a defined project or developed inside a wider assignment. An initial review can first expose the highest-value changes.
Typical entry point: manual validation, weak logs, hard-to-repeat results.

workflow Device and subsystem evaluation path

Device and subsystem evaluation

Need to judge a new IC, module, reference design, or subsystem in its real operating context?


Reference designs are useful starting points, but “copy the datasheet circuit” is not the same as validating the implementation. Loading conditions, clock ranges, layout assumptions, control-loop stability, sequencing, support components, and interface timing can all change the result once the part is placed inside your system.


When a “should just work” device does not behave as expected, I go back through the datasheets, app notes, operating limits, and setup assumptions. The aim is to separate valid reuse from places where the numbers need to be checked properly: compensation values, timing margins, biasing, signal levels, register setup, or measurement conditions.


The useful output is a clearer decision: fit for use, correction path, measurement uncertainty, or redesign risk.

Engagement path: Assumption-checking can begin as a bounded review; bench proof, correction work, or integration can continue as a defined project or development assignment.
Typical entry point: component choice, reference-design risk, early integration uncertainty.
Device and subsystem evaluation path
  • Engagement path
    • Diagnostic start when the first need is assumption-checking
    • Development or defined-project support when the device must be proven or corrected on the bench
  • Entry
    • New IC, module, reference design, or subsystem
    • “Should work” expectation is not matching bench behaviour
  • Re-check assumptions
    • Datasheet, app note, loading, clocks, limits, sequencing
    • What was copied, adapted, or left implicit
  • Confirm in context
    • Measure the real operating region, not just the reference case
    • Check timing, biasing, compensation, register setup, support parts
  • Exit
    • Fit, correction path, measurement uncertainty, or redesign risk is explicit
workflow Measurement-led investigation path

Measurement-led investigation

Progress is limited by missing, noisy, inconsistent, or weakly structured evidence?


The process may exist on paper, and the required data points may already have been flagged in review, but bench visibility can still be too manual, fragile, or multi-step. Raw signal has to become data you can capture, log, compare, and trust.


Often the approved flow does not need to be replaced. It can be augmented: oscilloscope captures exported with as-used settings, quick setup recall, scripted measurement sequences, cleaner result logging, or small utilities that remove repeated manual averaging, offset adjustment, and copy-paste work.


I assess where the existing setup can be made more repeatable without turning every bench task into a full ATE project.


The useful output is evidence that is captured, comparable, and good enough to support the next decision.

Engagement path: The work can start by reviewing weak evidence, continue through new capture and investigation, and become a reusable validation or automation project where needed.
Typical entry point: manual captures, weak logs, awkward comparison between runs.
Measurement-led investigation path
  • Engagement path
    • Diagnostic start when existing evidence is weak or inconsistent
    • Development support when new capture, firmware, or bench work is needed
    • Defined project when the measurement path must become reusable
  • Entry
    • Evidence is missing, noisy, inconsistent, or hard to compare
    • An approved flow exists, but bench visibility is weak
  • Turn signal into evidence
    • Capture settings, raw data, run metadata, and environment context
    • Remove repeated averaging, offset, screenshot, and copy-paste steps
  • Keep disruption low
    • Script or augment the existing setup before rebuilding it
    • Prioritise repeatable comparison between runs
  • Exit
    • Evidence is captured, comparable, and useful for the next decision
workflow RF / firmware bring-up path

RF / firmware bring-up path

The RF hardware is plausible, but the control path is still blocking progress?


A radio can be held up even after the visible RF path looks correct. Matching may be characterised, VNA data may look sensible, filters may be close to target, and the right parts may already be fitted. The remaining blocker may be the backend control scheme: LO selection, VCO lock, PLL programming, gain states, band cases, or register sequencing.


I help at that RF/firmware boundary, usually by adding temporary debug access or controlled test hooks rather than disturbing the production architecture. That may mean locating hard-coded configuration assumptions, adding a new band case, exposing register-level control, building a debug handler for live PLL setting import/export, or scripting controlled sweeps so measured RF behaviour can be tied back to firmware state.


The goal is to prove the control path at the bench: what firmware commanded, what the RF IC or synthesizer accepted, whether lock was achieved, what the instrument measured, and which change actually moved the result.


The useful output is a cleared or identified control blocker, with RF behaviour linked back to firmware-visible state.

Engagement path: RF and firmware work can sit inside a wider bring-up assignment, become a defined control-path deliverable, or begin with a review of register notes, captures, and setup evidence.
Typical entry point: LO/VCO/PLL control, RF IC register visibility, new band bring-up.
RF / firmware bring-up path
  • Engagement path
    • Development support when RF behaviour must be tied to firmware state
    • Diagnostic start when logs, register notes, captures, or setup details already exist
    • Defined project when the output is a control hook, sweep script, register path, or evidenced bring-up result
  • Entry
    • RF path looks plausible, but backend control still blocks progress
    • Lock, band case, register, gain-state, or sequencing uncertainty remains
  • Expose control state
    • LO selection, VCO lock, PLL programming, RF IC registers
    • Temporary debug hooks or live setting import/export
  • Tie command to measurement
    • What firmware commanded, what the device accepted, what the instrument measured
    • Which change actually moved the RF result
  • Exit
    • RF behaviour is linked back to firmware state
    • Control blocker is identified or cleared
